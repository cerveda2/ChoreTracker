# Release Readiness Backlog (ordered by priority)

Items needed before (and for) Google Play publication. Some are useful well before launch. Keep this file in sync when completing items (mark done with strikethrough), same as the Feature Backlog in CLAUDE.md.

### Phase 1 — Useful Now (add during active development)

1. ~~**Crashlytics + Analytics**~~ — Done. `FirebaseConventionPlugin` wires both SDKs; collection disabled in DEBUG builds.
2. **Analytics events** — Instrument key user actions with `FirebaseAnalytics.logEvent()`: sign-in/sign-up, household create/join, chore logged, chore added/edited/deleted, member invited/removed. Gives visibility into real usage before launch.
3. ~~**Release build hardening**~~ — Done (`chore/release_build_hardening`). Release has `isMinifyEnabled = true` + `isShrinkResources = true` (`isDebuggable` is already false by default). A new CI job (`assemble-release`) builds an unsigned release on every PR (`assembleRelease -x uploadCrashlyticsMappingFileRelease`) so R8/shrinker breakage fails before merge. The first R8 build needed no app keep rules: Firestore is mapped by hand (no `toObject`), there's no `@Serializable` (kotlinx-serialization-json is on the classpath but unused), navigation uses string routes, and Hilt/Room/WorkManager/hilt-work/CameraX/ML Kit ship consumer rules. Enums persisted by `.name` (`ThemeMode`, `ChoreCategory`, `HouseholdRole`, `AppError`) are safe — R8 keeps the constant-name strings. Smoke-tested on an emulator (preview flows, theme persistence, forced reminder-worker run); signed-in flows (Firestore sync, QR scan/render, release push, account deletion) still need a real-device pass before the first Play upload.
4. ~~**ProGuard/R8 rules**~~ — Done. `app/proguard-rules.pro` keeps `SourceFile,LineNumberTable` (renamed to `SourceFile`) per Crashlytics' documented setup; the Crashlytics plugin uploads the mapping file for minified builds. `core/notifications/src/main/res/raw/notifications_keep.xml` `tools:keep`s the three `invite_accepted_notification_*` strings, which the FCM SDK resolves by name from the push's `titleLocKey`/`bodyLocKey`.
5. ~~**Signing config**~~ — Done. `app/build.gradle.kts` reads `choretracker.release.storeFile`/`storePassword`/`keyAlias`/`keyPassword` via `providers.gradleProperty` (configuration-cache friendly, same pattern as `choretracker.firebase.*`) — set them in `~/.gradle/gradle.properties` locally or pass `-P` in CI. Without them the release build is left unsigned (`app-release-unsigned.apk`), never debug-signed. The upload keystore lives outside the repo (`*.jks`/`*.keystore` are gitignored); Play App Signing holds the actual app signing key.
6. ~~**Version bumping strategy**~~ — Done (`chore/release_pipeline`). `version.properties` stays the single source of truth (`versionName` = `major.minor.release`, `versionCode` = `MMmmRRbb`, per the file's own header comment); it's bumped by hand in a PR, and a release is the tag `v{major}.{minor}.{release}+{build}` on the merged commit — `release.yml` fails if the tag and the file disagree. See CLAUDE.md → Releasing.

### Phase 2 — Pre-Launch Essentials

1. ~~**Localization (i18n)**~~ — Done. All user-facing strings live in `core/design`'s `values/strings.xml` (257 keys) with a full `values-cs/` (Czech) translation kept at 1:1 parity — verified after every string change throughout the redesign, and lint-enforced (`ci_gotchas` memory: Czech i18n is ERROR severity, not warning). Error messages were the exception until `bugfix/localize_error_messages`: `AppResult.Error` now carries a typed `AppError` (`core/model`), Firebase exceptions are classified by `Throwable.toAppError()` (`core/remote-firebase`), and the UI resolves text via `AppError.toStringRes()` (`core/design`) — no hardcoded or raw Firebase English reaches the UI. Notification channels, the invite-accepted push (FCM `titleLocKey`/`bodyLocKey` resolved against `core/notifications`' own resources), the "System default" language label and the preview-mode default name followed in `bugfix/localize_remaining_strings`. Still English by design or out of reach: data-layer defaults with no resource access (`"My Household"` fallback, preview household `"Sunny Flat"`, the stats placeholder `"Household"`).
2. **Privacy policy + Terms** — Required by Google Play. Host on a simple webpage (GitHub Pages works). Link from app settings screen and Play Store listing.
3. **App icon + adaptive icon** — Production-quality launcher icon with foreground/background layers for adaptive icon support. Current icon may be template.
4. **Google Play Store listing assets** — Screenshots (phone + tablet if supported), feature graphic (1024x500), short/full descriptions, categorization.
5. **`google-services.json` security** — Currently committed to git. Move to gitignored location, provide via CI secret or local-only path. Not a hard blocker (Firebase keys are meant to be in APK) but best practice.

### Phase 3 — CI/CD & Release Automation

1. ~~**Release CI workflow**~~ — Done. `.github/workflows/release.yml` on a `v*` tag: verifies tag == `version.properties` and that the commit is on `main`, builds the upload-key-signed AAB + APK (keystore from the `RELEASE_KEYSTORE_BASE64` secret, passwords from `RELEASE_STORE_PASSWORD`/`RELEASE_KEY_PASSWORD`, no configuration cache so they never land in a cache entry), verifies the APK signature, creates a **draft** GitHub Release with the AAB/APK/`mapping.txt` (draft because the repo is public and workflow artifacts would be publicly downloadable), then deploys the production backend via the reusable `deploy-firebase.yml`. Production rules/indexes/functions no longer deploy on every push to `main` — only with a release or a manual `prod` dispatch on `main`. Unit tests aren't re-run; the tagged commit already passed CI on `main`.
2. **Fastlane or Gradle Play Publisher** — Automate AAB upload to Google Play internal/beta/production tracks. Manage changelogs, screenshots, metadata in repo.
3. ~~**Auto version bump on release**~~ — Replaced by a manual bump in a PR plus the tag/`version.properties` check in `release.yml` (no bot commits to `main`).

### Phase 4 — Post-Launch Polish

1. **In-app update (Play Core)** — Prompt users to update when new version available. `com.google.android.play:app-update`.
2. **Firebase Performance Monitoring** — Track screen load times, network latency, slow frames. Useful once real users exist.
3. **Remote Config** — Feature flags for gradual rollouts. Useful at scale.
4. **ANR & vitals monitoring** — Play Console vitals + Crashlytics ANR tracking. Comes mostly free with Crashlytics.
5. **Accessibility audit** — Content descriptions, touch targets (48dp min), screen reader support, contrast ratios. Required for good Play Store rating. *Partial pass done during the redesign's Phase 8*: every icon-only interactive control has a real `contentDescription` (verified by grep — no `IconButton`/clickable icon has `contentDescription = null`; decorative icons paired with adjacent visible text correctly stay null), touch targets use M3's `IconButton`/`FilledTonalIconButton` defaults (48dp min, never overridden smaller), `SectionHeader` now carries `Modifier.semantics { heading() }`, and dark-mode contrast was spot-checked across every top-level tab plus the completion/chore-history detail screens. Not done: a full screen-reader (TalkBack) walkthrough and a formal contrast-ratio audit.
6. **Tablet / foldable support** — Adaptive layouts for larger screens. Google Play flags apps that don't handle tablets well.
7. **Data export / account deletion** — *Account deletion done* (Phase 9c, PR #94): "Delete account" in the Account screen's Danger zone → a callable `deleteAccount` Cloud Function (`functions/`, `europe-west1`, Admin SDK — no re-auth prompt) that tears down household membership (sole-owner → recursive household delete; owner-with-co-member → transfer then soft-remove; non-owner → soft-remove), deletes `users/{uid}`, then the auth user last. Shipped as part of the Phase 9 membership & account lifecycle work (9a soft removal, 9b leave/transfer, 9c deletion — integration branch `feature/member_lifecycle`). Still open: **data export** (Play doesn't require it, but it pairs naturally here).
8. ~~**Chore reminders**~~ — Done. See Feature Backlog item 7 in CLAUDE.md (implemented together as one feature).
